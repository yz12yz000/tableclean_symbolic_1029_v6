# 机器人收桌面系统功能与任务规划说明

## 1. 文档目的

本文用于说明当前机器人收桌面项目已经具备的功能，并明确未来任务规划系统中，哪些工作适合交给大语言模型（LLM），哪些工作应继续由本地程序作为确定性的 symbolic model 处理。

这里的 symbolic model 可以理解为一个具有明确状态、规则和安全检查的本地任务执行系统。它不依赖语言推理来决定机械臂的具体动作，而是根据相机观察结果和几何规则计算可执行动作。

## 2. 当前项目的整体流程

当前的收托盘流程可以概括为：

1. 相机观察桌面、碗和托盘。
2. 视觉系统识别桌面上的碗以及托盘位置。
3. 深度点云估计每只碗的中心、碗沿、大小和测量误差。
4. 判断每只碗是在桌面上，还是已经在托盘中。
5. 按任务规则选择下一只需要处理的碗。
6. 在托盘内部搜索可以放置的位置。
7. 根据实际抓取点和碗中心计算放置时的水平偏移。
8. 使用原来的夹碗沿方法和七段抓放动作完成一次抓取与放置。
9. 机械臂返回观察位置。
10. 重新观察并确认这只碗是否真的已经放入托盘。
11. 更新托盘占用状态，再决定是否处理下一只碗。

如果目标没有被确认放好，系统不会直接处理下一只，而是继续观察、停止或报告异常。

## 3. 当前项目已经具备的功能

### 3.1 碗和托盘的视觉识别

系统可以识别桌面上的碗和托盘。托盘使用独立的 YOLO 分割模型，再结合深度图、相机参数和坐标变换，得到托盘在机器人坐标系中的位置、方向和边界。

托盘可以在两轮观察之间移动。程序每轮都会重新计算托盘位置，因此不会一直使用旧的绝对坐标。

当前附带的托盘模型针对已经记录的花纹托盘和当前相机视角。它属于现场参考模型，不代表任何形状和外观的托盘都能直接识别。

### 3.2 自动估计碗大小

程序复用原有的碗沿点云拟合方法，自动估计：

- 碗中心位置；
- 碗沿位置；
- 碗的外部占用半径；
- 估计误差和可靠程度。

因此更换碗之后，不需要提前在配置文件中填写这个碗的直径。

如果碗沿点云不完整、反光严重、被遮挡，或者拟合结果不稳定，程序会要求重新观察或停止，不会强行使用一个猜测的大小。

### 3.3 原有的碗沿抓取方法

抓取方式保持原来的设计：

- 视觉找到碗；
- 点云找到碗沿；
- 生成多个可能的夹取候选；
- 机械臂夹住碗沿；
- 抬升并移动碗。

抓取候选由本地视觉和几何算法产生。大语言模型只需要指出“要处理哪只碗”，不需要决定夹爪的具体接触点。

### 3.4 大碗优先和顺序管理

当前收托盘流程默认优先处理较大的碗。同尺寸目标仍使用原来的距离排序。

这样做的目的是避免先放小碗，导致大碗最后没有足够的托盘空间。

例如，桌面上同时有大碗、中碗和小碗时，默认顺序是先放大碗，再处理中碗，最后处理小碗。

### 3.5 托盘内自动搜索空位

程序不会只使用几个固定的放置点，而是在托盘的局部坐标系中生成候选位置，并逐个检查：

- 碗是否完整位于托盘有效区域内；
- 是否越过托盘边界；
- 是否与已经放入的碗重叠；
- 是否满足碗与碗之间的间距；
- 放置当前碗后，剩余碗是否仍有可用位置。

如果托盘没有足够空间，程序会停止，并不会继续把碗放到已有碗上面。

当前空位搜索是一个有计算上限的启发式方法。它可以找到合理的空位，但不保证得到数学意义上的最优装箱方案，也不处理堆叠。

### 3.6 放置时的 XY 补偿

夹爪夹住的是碗沿，而不是碗中心。因此，夹爪到达某个托盘位置时，碗中心可能仍然偏离目标位置。

程序会根据以下信息计算放置补偿：

- 视觉测出的碗中心；
- 实际使用的抓取候选；
- 抓取点与碗中心之间的关系；
- 托盘中选定的目标位置。

如果一个抓取候选无法规划，程序可以尝试其他候选，并为新的候选重新计算放置补偿。

### 3.7 放置后的连续确认

动作执行结束并不等于任务成功。程序会重新观察，并同时检查：

- 原来桌面位置的碗已经消失；
- 托盘中出现一个新的、大小相近的碗；
- 原来已经在托盘中的碗仍然存在；
- 新碗靠近本次选定的位置；
- 连续两次观察结果稳定。

只有满足这些条件，程序才把本次放置记录为成功，并允许继续处理下一只碗。

### 3.8 原来的单碗定点放置

原来的单碗功能仍然保留。它适合只处理一只碗，并将碗放到预先示教好的位置，例如左上、左下、中间、右上、右下或 blue 位置。

新的托盘收纳功能和原来的单碗定点放置是两种不同的任务模式，可以分别使用。

## 4. 本地 symbolic model 维护的状态

本地程序会维护以下状态：

- 当前桌面上有哪些目标；
- 每个目标的位置和大小；
- 每个目标的视觉可靠程度；
- 哪些目标仍在桌面上；
- 托盘的当前位置和方向；
- 托盘中已经有哪些碗；
- 托盘中哪些位置已经被使用；
- 上一次抓放动作是否等待确认；
- 还有哪些目标没有处理；
- 托盘是否已经没有可用空间。

它还会执行明确的保护规则：

- 目标位置不确定时不强行抓取；
- 托盘无法定位时不执行放置；
- 目标已经在托盘内时不重复抓取；
- 上一次放置未确认时不开始下一次抓取；
- 托盘没有空位时停止；
- 机械臂动作发生执行错误时停止并报告。

## 5. 适合由 LLM 负责的内容

LLM 适合负责高层任务理解和任务策略，而不是直接控制机械臂。

它可以处理以下内容：

- 理解用户想收拾哪些物体；
- 判断“所有碗”“绿色碗”“碗和杯子”等目标范围；
- 理解用户指定的颜色、类别和优先级；
- 选择使用哪个托盘；
- 决定大碗优先、杯子最后等处理顺序；
- 判断是否需要处理其他类别的物体；
- 在多个任务之间安排先后；
- 根据本地返回的失败原因决定是否重新安排任务；
- 用自然语言向用户解释任务结果。

例如，用户说“先把大碗放进左边托盘，再放杯子”，LLM 可以把它理解为：

- 目标类别包括碗和杯子；
- 目的地是左边托盘；
- 碗优先于杯子；
- 碗内部按大小从大到小处理；
- 使用托盘自动空位搜索；
- 放置没有确认时停止继续抓取。

LLM 也可以根据本地程序返回的状态做高层决策。例如本地程序报告托盘已满，LLM 可以提示用户更换托盘，而不是继续要求本地程序强行放置。

## 6. 应继续由本地程序负责的内容

以下内容应继续由本地 symbolic model 和机器人执行器负责：

### 6.1 几何计算

包括碗中心、碗大小、托盘边界、空位位置、抓取点和放置补偿。这些计算依赖实时视觉、深度数据、坐标变换和标定结果，不适合由 LLM 直接推测。

### 6.2 安全检查

包括托盘边界检查、碗之间的间距检查、工作区检查、位姿有效性检查和路径规划检查。

LLM 可以提出目标，但不能绕过这些检查。

### 6.3 抓取和运动执行

包括抓取候选选择、七段动作规划、夹爪开合、机械臂移动、下降、释放、抬升和返回起点。

LLM 不应直接输出关节角、机械臂坐标或夹爪控制指令。

### 6.4 成功判断

只有本地视觉程序能够根据前后两次观察判断碗是否真的落入托盘。LLM 不应把“机械臂已经运动完毕”当作“物体已经放好”。

### 6.5 异常停止

托盘消失、深度无效、碗沿无法估计、规划失败、动作失败或放置无法确认时，应由本地程序先停止并保护现场，再把结果交给 LLM 解释或重新规划。

## 7. 推荐的系统分层

推荐把系统分为三层：

### 第一层：用户和 LLM 任务规划层

负责理解用户意图，并形成任务要求，例如：

- 收拾哪些类别；
- 使用哪个托盘；
- 先后顺序；
- 是否允许跳过无法识别的目标；
- 托盘满后如何处理。

### 第二层：本地 symbolic model 层

负责把任务要求和实时视觉结果结合起来，维护当前场景状态，并执行确定性的规则：

- 识别目标状态；
- 选择具体目标；
- 搜索托盘空位；
- 计算抓取和放置几何；
- 检查是否可以执行；
- 记录动作是否已经确认成功。

### 第三层：机器人执行层

负责执行本地程序生成的合法动作：

- MoveIt 路径；
- 机械臂七段动作；
- 夹爪控制；
- 返程；
- 停止和错误反馈。

LLM 不应越过本地 symbolic model 直接访问第三层。

## 8. 推荐的 LLM 与本地程序接口

本地程序可以向 LLM 提供场景摘要，包括：

- 目标编号；
- 目标类别和颜色；
- 估计大小；
- 目标所在区域；
- 是否可以抓取；
- 托盘编号和可用尺寸；
- 当前托盘占用数量；
- 本地支持的抓取和放置能力；
- 当前是否存在未确认动作。

LLM 返回的内容应当是任务要求和策略，例如：

- 要处理哪些目标；
- 使用哪个托盘；
- 目标处理顺序；
- 是否自动搜索空位；
- 是否遇到未确认动作就停止；
- 托盘满后是停止、换托盘还是等待用户处理。

本地程序收到这些要求后，必须进行格式检查、目标检查、几何检查和安全检查。检查通过后才生成实际机械臂动作。

## 9. 最重要的设计原则

LLM 负责回答：

> 用户想完成什么任务，应该先处理什么，使用哪个目的地，以及遇到异常时采取什么高层策略。

本地 symbolic model 负责回答：

> 当前看到了什么，具体抓哪里，具体放哪里，这个位置是否可行，动作是否安全，以及物体是否真的放成功。

这种分工可以同时保留 LLM 的灵活理解能力和本地程序的几何准确性、执行稳定性与安全检查能力。
