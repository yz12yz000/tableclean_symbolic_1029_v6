# Upgrade 方案：Agent 规划收纳，机器人逐件抓放、回初始位再观察

更新日期：2026-10-29。本版按单相机、静态桌面条件修订，只更新方案，尚未实施 Upgrade。前置的 [最小 Debug 修复](DEBUG_PLAN_20261028.md)已完成代码修改和针对性检查，尚未做新的实机验证。

## 一、修改目标与现场条件

把 `gat_local_new` 改造成与当前 `table_clean_ws` 交互的任务规划库。Agent 决定收哪些物体、先后顺序、每件放在哪里，以及怎样为剩余物体留出空间。本地 Symbolic Model 和运动模块负责具体抓法、精确姿态、释放动作和路径验证。

本版按用户明确的现场条件设计：

- 只有一个相机。机械臂在初始位时不挡桌面；运动途中可能遮挡目标。
- 其他物体不会自行移动，也不考虑人为移动；场景变化来自本任务的抓放。
- 只在初始位静止后获取用于下一步决策的新观察。运动途中不依赖 YOLO 或 Agent 看图。
- 每次只执行一件，完整抓放并回初始位后，再更新剩余计划。
- 本版不设计托盘容量不足后的换托盘、分批处理、重排已收物体或堆叠方案。基本几何检查仍保留；当前没有可行安排时如实报告。

这里的 Agent 项目是 `/home/rob/table_clean_ws/gat_local_new`，不是旧的 `6_GAT_Edu/gat_local`。

## 二、先说明当前碰撞检查，以及本版需要补什么

### 1. 当前已经有的检查

| 层次 | 当前代码做什么 | 能说明什么 |
|---|---|---|
| 托盘空位 | `placement_grid.py` 检查目标范围、边界和与已有占用的间距 | 最终位置在平面上是否有空间 |
| 抓取候选 | `candidates.py` 依次尝试候选，完整路径未通过时不执行 | 可在运动前换本地抓法 |
| 机器人运动 | `moveit_ros.py` 调用 MoveIt 的 IK、轨迹规划和状态有效性检查；检查轨迹采样点、关节限制及终点 | 机器人相对当前规划场景是否有效 |
| 分段执行 | 每段执行前核对关节起点、控制状态，并再次检查轨迹采样点 | 不盲目执行与当前机器人状态不符的轨迹 |

机器人碰撞检查只对规划场景中实际存在的几何有效。当前执行链路未见将每轮所有识别物体与夹持物体自动写入 MoveIt 的完整实现；`_scene()` 主要读取场景并清理指定旧模型。外部场景、OctoMap、URDF 中的模型可能另有覆盖，实施时先核对，不能据此断言完全没有环境碰撞检查。

现有逐段复核不等于逐段重新拍摄。相机被挡时，仍可用已建立的场景和机械臂关节反馈检查运动。

### 2. Agent 与本地模型怎样分工

Agent 可以看出“这里太挤”“先放这一件可能挡住另一件”，据此选择位置和顺序。但图片里的视觉判断不能证明夹爪、手臂和被夹物体在三维轨迹中都不会碰。

因此：Agent 做布局与顺序判断，也可以调用预览工具；本地做数值几何、运动可达性和碰撞检查，返回具体原因，由 Agent 改计划。实际 MoveIt 计算属于本地运动模块，不需要由大模型重新实现。

### 3. 采用够用的简化表示，不建设复杂的实时系统

先复用现有 MoveIt 和已有模型；核对缺口后，仅补齐影响这次桌面抓放的简单几何：

- 碗、杯等物体：使用尺寸和高度范围对应的保守圆柱或其他简单外包形状。
- 桌面、托盘：使用实测位置、高度和简单平面／盒体；托盘内部允许放置的空间应保持可用，不能把整个托盘容积当成实体堵死。
- 夹爪：先核对 URDF 中已有碰撞几何是否覆盖实际开合范围；确有缺口再补简单包络，不重复叠加未经标定的旧模型。
- 夹持物体：搬运时把它的体积和相对夹爪的偏移纳入检查，避免只验证空夹爪的路径。

这些几何需要可信尺寸、高度和坐标变换。现有半径、碗口高度可以复用，缺少的高度／支撑面参数再针对性补足，不能凭图片猜一个尺寸当成标定值。

优先让已有运动检查使用这些简单表示。夹持和放置的接触应按阶段明确处理：目标仍在桌上 → 夹取后随夹爪移动 → 释放后作为托盘占用。预规划时模拟这几个状态，实际执行按已完成的动作阶段同步；不能全程把同一物体同时当作桌面障碍和夹持物体。夹指与目标、物体与支撑面的必要接触不能用“全局关闭碰撞”解决，也不能被粗糙外包形状误判为所有抓法都不可用。

不引入运动中视觉跟踪、连续点云重建、复杂物理仿真或所有顺序的穷举。简化几何与现有检查够用时，停止扩展。

## 三、完整运行流程

1. **初始位观察。** 机械臂静止，相机取得同一轮 RGB-D，YOLO 和几何模块识别物体、尺寸、托盘及占用。
2. **Agent 制定整体安排。** 根据用户目标和场景，确定物体清单、顺序和每件的预留位置。
3. **本地检查。** 检查整份布局是否冲突，以及后续是否有基本下降、释放和撤离空间；必要时对下一件做一次假设预览。当前要执行的一件必须通过完整路径检查。
4. **执行一件。** 使用这一轮已确认的场景完成抓取、搬运、释放、撤离和回初始位。过程中继续读取机器人和夹爪反馈，不要求相机看清桌面。
5. **初始位重新观察。** 返回后确认静止，再拍摄；按实际结果更新已放位置和剩余物体。相机遮挡造成的运动中漏检不参与占用删除。
6. **Agent 复核剩余计划。** 原位置仍可用就保留；落点偏移或新占用造成冲突，就修改尚未执行的安排，再交给本地检查。
7. 重复上述过程，最后在初始位看图并结合本地结果确认完成，或说明未处理原因。

在本版静态桌面前提下，不在每个动作中途增加视觉检查，也不因为 Agent 多想了一次就强制重拍。若观察已经超过有效期、反馈异常或任务恢复，则在仍处于初始位时重新获取场景，不能使用过期动作引用。

## 四、修改对象一：gat_local_new

### 1. 修改 Agent 的规则

对象：`.opencode/agent/gat-table.md`，同步 `/table` 命令说明、相关部署规则与项目文档。

具体修改：由“每轮选一个 object_id 和 slot_id”变成“先安排整份任务，再逐件执行”。Agent 必须读取新画面和场景，列出任务内支持物体，为它们分配位置和顺序，并在每次回初始位后复核。

“大物体优先”“靠边留空间”作为参考，不覆盖 Agent 的决定。Agent 可以提出某种顺序可能更好，并请求本地检查；收到位置冲突或路径失败后，由 Agent 重新选择，不让 runner 悄悄替换目标。

### 2. 保存计划与执行进度

对象：`tools/table_session.py` 对应的会话数据及计划文件。

增加一份包含物体身份、顺序、预留位置、完成状态和计划版本的记录。例如“绿碗先放 A、白碗后放 B”；绿碗完成后保存实际落点，白碗仍保留或改选 B。

预留和实际占用分别记录。计划里的 B 只表示为白碗留位，真实运动场景中不能把那里当成已经有一只白碗。每轮编号通过现有位置、尺寸和上一步动作关联到任务内物体；歧义时回到观察，不新增复杂追踪系统。

### 3. 扩展交互工具

对象：`tools/table_session.py`、`reference/table_round.schema.json`、`generated/table/` 中的校验代码。

在现有 start、poll、submit、cancel 基础上支持四类交互：

| 交互 | 用途 |
|---|---|
| 提交／修改整体计划 | 把全部待处理物体的位置和顺序交给本地检查 |
| 请求候选或假设预览 | 候选不足时查其他区域；紧凑布局时检查下一件是否能放入 |
| 执行当前一件 | 使用已接受计划中的本轮物体和目标，单独发出执行请求 |
| 读取放后结果并复核 | 在初始位取得新图片、真实占用和确认结果，继续或修改计划 |

同一轮允许多次计划检查，消息需有独立编号；执行消息只消费一次。继续使用本机文件、后台 worker 和 OpenCode 已配置的模型，不增加网络服务或另一个模型客户端。

## 五、修改对象二：table_clean_ws

### 1. 在初始位输出用于规划的场景

对象：`tools/test_live_place_pipeline.py`、`tools/table_round_io.py`；必要字段缺失时再改 `src/yolo_vision/yolo_vision/main.py`。

保留“回初始位、确认静止、取得新观察”的顺序。向 Agent 提供同轮原图、清晰标注、物体尺寸与身份、托盘范围、已有占用、候选位置、可用操作及上一动作结果。

当前任务策略只接受 `all_bowls`，视觉配置还把 cup/plate 合并为 bowl。升级时同步调整 `tools/table_agent_protocol.py` 与两侧任务校验器，使目标清单能表达“用户希望收的物体”和“本地实际支持的物体”。支持能力要由本地几何和操作条件给出，不能由 Agent 看到类别就认定能抓。

先执行当前已验证的碗类抓放；计划格式允许更多物体。摆放方向也只能选择本地已有的方式，当前固定释放姿态不等于已经支持任意旋转摆放。

### 2. 提供候选位置，并检查 Agent 的整份安排

对象：`src/yolo_vision/yolo_vision/placement_grid.py`、`tools/place_rounds.py`。

复用现有网格和尺寸计算，向 Agent 提供分布在不同区域的少量候选，不只截取相邻的前三个。每个候选说明占用范围、边缘余量和验证程度；需要时查询其他区域。

收到整份计划后，检查每件的位置、物体之间的间距、与已有占用的冲突，以及任务目标是否重复或遗漏。再检查目标附近的夹爪进入、释放和撤离余量，避免只证明碗底摆得开。

本地返回“白碗 B 与绿碗 A 的范围冲突”“白碗 B 没有足够释放空间”等结果；由 Agent 决定怎么修改，不在本地另建负责整体顺序与布局决策的 Agent。

Debug 已修改的现场占用规则继续使用：绿色碗已在托盘上时，不因其保守圆碰边再次拒绝整轮，但保留完整避让范围。

### 3. 补齐必要的静态场景几何，复用现有运动检查

对象：`src/grasp_executor/grasp_executor/moveit_ros.py`、`candidates.py`、`grasp.py` 及 runner 传递给执行器的场景数据；必要时增加一个小的场景几何转换辅助文件。

先列出实际加载的机器人、夹爪、环境和外部场景模型，查明哪些物体已经覆盖。现有场景清理只针对指定旧对象；新模型不能与旧对象 ID 混用，也不应删除无关外部障碍物。

按第二节的简单表示补实际缺口，并处理抓取前、夹持中、释放后的几何状态。当前一件的七段路径仍先完整规划、采样检查，再执行；保留每段前的关节和控制状态复核。

每轮抓放期间，未被抓物体维持初始位观察得到的位置；目标物体随动作阶段更新。释放后的撤离与回位预规划使用计划落点和已验证的放置误差范围，回初始位的新观察再替换为实际落点。不能把一个未经验证的“放置误差为零”假设带进撤离检查。

这部分补的是场景表示和阶段一致性，不重写 MoveIt，不把图片判断当作碰撞通过的凭据。

### 4. 提供有限的后续动作检查，不依赖中途观察

对象：`tools/place_rounds.py`、runner 的预览入口，以及现有执行器的 plan-only 能力。

默认先检查整份布局和下降／释放／撤离余量。对于明显紧凑、邻近或 Agent 有疑问的安排，再允许预览下一件，而不是默认把所有排列都规划一遍。

例如机械臂还在初始位时，Agent 提出“先绿碗 A，再白碗 B”。本地在当前场景的独立副本里假设绿碗已从桌上移到 A，再调用已有规划器检查白碗 B 的关键动作或完整路径。失败就反馈给 Agent 改顺序或改位置。

这一过程是计算预览，不是真抓绿碗，也不需要机械臂运动中拍摄。假设场景必须与真实执行场景隔离；若使用共享规划服务，调用需串行、确认恢复，且不能让执行线程使用假设占用。预览超时或清理失败不产生可执行计划。

假设预览通过，只代表按该假设可能可行。实际绿碗放完仍须回初始位观察，再根据实际占用重新验证白碗；不能直接复用旧假设轨迹发动作。

### 5. 回初始位后交回 Agent，清楚区分失败类型

对象：`tools/test_live_place_pipeline.py`、`tools/place_rounds.py` 和动作结果消息。

正常动作完成后，由现有流程确认回位，再重新观察并更新剩余计划。放歪但位置仍能可靠确认时，按实际占用调整下一件。

运动前不可达可以由本地换抓取候选，候选耗尽后交 Agent 改位置或顺序。动作已发出后失败、未能回位、可能仍夹着物体或位置不明时，保留停止和说明原因；本版不设计复杂的自动故障恢复。不能为了拍到无遮挡图，就从未知状态自动执行一段未经验证的回位。

已有夹爪开合反馈不等于独立抓牢证明。确认信息如实保留，不能因 Agent 希望继续而把失败改成成功。

### 6. 同步双方协议和版本

对象：`tools/table_round_protocol.py`、任务策略与请求发布代码，以及 gat_local_new 的 schema、校验代码和 Agent 文档。

消息区分整体布局检查、假设预览、真实执行和放后复核；绑定任务、场景、计划版本和物体身份。新场景生成后旧的执行引用失效，整体布局思路可以保留并重新绑定。

沿用一个持续 runner，保留超时、总预算、取消和重复提交保护。假设预览次数受预算限制。更新协议后重新做在线预览，不用旧版本基线直接执行。

## 六、修改后的验收顺序

| 顺序 | 检查内容 | 预期结果 |
|---|---|---|
| 1 | 复用已完成 Debug | 已放绿碗不因保守圆碰边阻塞白碗，仍作为占用避让 |
| 2 | Agent 与本地无运动交互 | Agent 读图提交两只碗完整安排；收到冲突后由 Agent 修改 |
| 3 | 简单场景与当前一件路径 | 覆盖已有占用、夹爪、夹持物体及释放撤离；不依赖中途相机 |
| 4 | 一次有限假设预览 | 在初始位计算“绿碗 A 后白碗 B”；冲突反馈有效，真实场景未被污染 |
| 5 | 放后新场景与计划调整 | 返回初始位的新观察更新实际落点，Agent 保留或修改白碗位置 |
| 6 | 用户恢复测试后的实机流程 | 每件都完成抓放、回位、观察、复核；保存计划和实际结果 |

先以两只碗验证，再增加当前能力支持的物体数量。这个版本的重点是初始位观察下的整体规划和逐件闭环；不扩大为实时视觉控制、复杂场景重建或容量不足的处理系统。
