# Debug 方案：用最小改动解除绿色碗的边界阻塞

更新日期：2026-10-29。本文的最小占用判断修复已实施，实施结果见下文；其他按需修复项尚未扩展。文件名保留原日期，便于原有链接继续使用。配套见 [Upgrade 方案](UPGRADE_PLAN_20261028.md)。

实施结果：修改 `tray_utils.py` 和 `place_rounds.py`，现场占用按有效中心归属，保守半径继续用于避让；新位置边界条件和现有两帧确认保留。补充两个针对性用例，所在测试文件共 8 项通过。用上次真实任务第 2 轮保存的 scene 做离线几何检查：绿碗由严格分类的 unknown 转为现场占用 inside，白碗仍为 outside，并产生 117 个几何合法空位。这些空位未做新的完整路径验证，不代表实机成功。运行环境解析到修改后的源文件；本次没有启动机械臂，也未重写历史确认结果。

## 一、修改目标

解决一个具体问题：绿色碗已经放到托盘，程序却因包含测量误差的占用圆碰到边界，将它标为“位置不确定”，导致白碗没有机会选位和执行。

修改后，已在托盘上的绿色碗作为已有占用保留下来，供白碗避让；不再用新物体入盘的完整边界条件反复否决它。白碗准备放入时，继续检查白碗的位置、与绿色碗的间距，以及抓放路径。

优先只改物体归属与占用衔接的少量逻辑，复用已有放后确认和两帧观察。其他问题只有在验证中仍然阻止运行时，再针对具体原因修复。

## 二、为什么要改这几个地方

现场第一张放后照片中，绿色碗的保守占用圆超出估计内边界约 4.2 毫米。这是模型对占用范围的估计，不是实体碗越界的精确测量。

当前程序把同一个“完整占用圆必须在托盘内”的判断，用在了两个不同问题上：

- 这个新位置是否适合放入白碗。
- 已经观察到的绿色碗是否属于托盘上的占用。

后一项不通过后，程序先停止整轮；后面的放置确认也只接受严格在边界内的物体。因此，只删除提前退出的判断还不够：必须让绿色碗同时进入后面的放置关联和占用记录，否则仍会确认失败，或者漏掉白碗需要避让的障碍物。

目前 5 毫米是规划预留量，50 毫米才是放置位置匹配容差。此前约 16.8 毫米的观察落点差没有超过匹配容差。这次不通过调大容差来解决问题。

## 三、修改哪个对象，具体怎么改

### 1. 修改“现场占用”的判断

修改对象：`table_clean_ws/src/yolo_vision/yolo_vision/tray_utils.py` 中物体归属判断，以及 `tools/place_rounds.py` 的调用处。

具体改法：给现场占用提供一个明确的判断方式。在托盘定位和物体定位有效的前提下，物体中心位于识别到的托盘区域，就可以登记为托盘占用；不再额外要求它包含误差的整个圆都落在托盘内。

这个判断只回答“这里已经有一个物体”，不声称证明了物体的力学稳定性，也不单独算作本任务抓放成功。中心在区域外、位置测不准的物体，不因这项修改自动通过。

实现上优先增加一个小的辅助判断，或给现有判断增加明确用途的参数；只在 session 识别现场占用时使用。新空位仍使用现有完整边界与间距检查。保守半径原样保留，不把绿色碗缩小，也不从障碍物中删除。

### 2. 让现有放后确认和占用记录使用这个结果

修改对象：`table_clean_ws/tools/place_rounds.py` 中 `ClearTableSession.observe()`。

具体改法：新判断认可的绿色碗，进入同一份托盘占用列表；放后匹配、已有占用更新和下一只物体的选位都使用它，避免一个环节认可、另一个环节仍标为 unknown。

刚执行完绿色碗时，保留已有确认条件：原位置不再有它，目标附近出现唯一匹配物体，原有占用仍在，连续两帧结果稳定。只有这些条件通过，才沿用现有流程更新完成数量、清除待确认动作，并处理白碗。

已经确认的绿色碗，继续用现有 `known_inside` 记录位置和范围。仅因占用圆靠近托盘边缘，不再阻断白碗。绿色碗真的消失、移动到无法可靠定位的位置，或白碗本身位置无效，仍按具体问题处理。

### 3. 同时覆盖“新开任务，绿色碗本来就在托盘上”

修改对象：仍是上述现场占用判断和 `ClearTableSession.observe()`，不增加跨任务数据库。

具体改法：任务第一次观察也按同样规则登记已有占用。这样即使上次任务已经结束，新开的白碗任务也能识别托盘上的绿色碗，不依赖上一任务的内存记录。

初始就存在的绿色碗仅计为已有占用，不增加本任务的成功抓放数量，也不把它重新选为待收目标。

### 4. 做少量针对性验证

修改对象：现有物体分类、session 与放后确认测试；优先复用 `test_tray_utils.py`、`test_clear_table_policy.py`、`test_visual_clear_table.py` 中的测试结构。

需要验证的行为：

| 场景 | 应有结果 |
|---|---|
| 绿色碗刚放下，仅保守圆超出内边界 | 可以进入已有放后确认；确认后白碗获得选位机会 |
| 新开任务时绿色碗已在托盘上 | 登记占用，不重复抓绿碗，不增加本任务完成数量 |
| 白碗目标与绿色碗范围重叠 | 拒绝该位置，继续检查其他位置 |
| 白碗自身目标超出托盘边界 | 仍拒绝，证明新目标检查没有被一起放宽 |
| 执行器返回成功，但绿色碗仍在原处或没有匹配落点 | 不计为放置成功 |
| 无效定位、旧帧、身份或数量异常 | 保留现有拒绝和重观察行为 |

用保存的场景数据复现本次边界问题；两帧逻辑另用明确标记的测试数据验证，不把重复使用同一张历史图冒充两次真实观察。

## 四、其他问题什么时候才修改

先完成上述最小修复，再做回放和预览。以下内容不预先扩展成新模块；只有确认仍挡住白碗才处理。

| 仍然出现的问题 | 最小处理方向 |
|---|---|
| 作业区域投影超出检测范围 | 查清哪个区域顶点越界；针对实际检测范围或投影错误修正，不能把错误直接忽略 |
| 白碗碗口拟合失败 | 核对这一帧的分割与深度；只修导致失败的环节，不整体更换识别算法或普遍放宽阈值 |
| 已放下绿碗无可抓候选，却被当成下一步的阻塞原因 | 占用定位可靠时，不要求它能再次被抓；仅调整这处抓取条件与占用条件的耦合 |
| 驱动无反馈或断连 | 先区分设备状态与程序故障；复现为代码问题才修对应位置，不在本次加入完整监控系统 |

本次不新增独立追踪框架、复杂状态机、全局布局算法或释放补偿。约 16.8 毫米偏差不能凭单次记录直接写成补偿量；如果它在后续测试中造成新的实际阻塞，再单独定位。

## 五、实施顺序与完成标准

先复现本次场景 → 修改现场占用判断 → 接通已有确认和占用记录 → 通过上述针对性测试 → 无运动预览 → 用户恢复现场测试后做实机验收。

最小代码范围预计是两个运行文件和对应测试。只有验证证明 runner 或其他文件也有同类阻塞，才扩大修改范围。

完成标准：绿色碗仅因保守圆碰边不再阻止白碗；绿色碗占用没有丢失；白碗仍接受自己的边界、避让和完整路径检查。若还剩别的错误，明确说明，不把这次 Debug 扩大为整个系统重写。
